# Trader 企业级优化路线图

> 本文是 trader 平台从"概念完整的自用系统"走向"企业级产品"的分步优化计划。
> 用法：按步执行，每个任务是一个独立可交付的改动；完成一项就在清单里打勾。
> 裁决标准沿用 VISION.md：这个选择让履历更可信、让归因更强吗？

## 1. 现状诊断（为什么优化）

系统概念和流程已经齐备（两个世界一座桥、三种运行模式、证据链），问题出在
**概念没有全部沉到代码结构里**。以下诊断均有代码证据。

### 1.1 后端：层在文档里，不在代码里

**渗漏①：业务计算和 SQL 写在 API 层 / 引擎层，领域概念有多份实现。**

- `api/resources.py` 的 `portfolio_curve` + `_daily_equity`（约 180 行）：组合净值、
  日频估值、交易日历补齐、K 线回填，整个写在路由文件里，并直接 `_connect()` 查 wallets。
- `engine.py` 的 `compute_metrics` 同样直接 `_connect()` 查 wallets，绕过 ledger。
- 结果："组合估值"一个概念至少两份实现，改一处必漏另一处。
- `_daily_equity` 里还有"日 K 数据滞后(本环境只到 08-18)"这类环境耦合注释。

**渗漏②：schema 没有版本，只有堆积。**

- DDL 散落在 9 个 store 的 `_init_db()`，迁移靠 `ALTER TABLE ADD COLUMN IF NOT EXISTS`
  逐条堆（runs.py 一处就有 12 条）。
- 类型不一致：`runs.prompt_versions` 建表是 TEXT，代码当 JSON 用；时间字段全是
  TEXT 存 ISO 字符串，无法做数据库级时间比较。
- `core/db.py` 每次查询新建 TCP 连接 + SET search_path，无连接池，多用户并发下是瓶颈。

**渗漏③：运行态还是"脚本思维"。**

- 9 个模块级单例（`default_runs/default_wallet/...`），无显式生命周期，测试靠
  schema hack 隔离。
- API 用 `subprocess.Popen` 拉起回放进程，日志重定向到文件，无任务状态管理。
- 日志靠 `print`，无级别、无结构化、无 trace 串联（前端信封里有 traceId，后端没有）。
- 架构决策寄生在代码注释里（"run 336 教训""8/24 盘前事故""附录 14 已定"），
  没有 ADR 机制承接。

### 1.2 前端：有 token，无治理

`index.css` 已经定义了设计 token（红涨绿跌、等宽数字、surface/border 色阶），
方向是对的，但三个缺口让它没有形成"系统"：

- **token 未贯穿**：自定义 `--accent: #175cd3` 与 antd 默认蓝 `#1677ff/#e6f4ff`
  在样式里并存；antd 组件未通过 ConfigProvider 对接 token；组件里仍有 inline style。
- **图标缺位**：导航用 emoji（🏠📈◾📦🗄️），这是最直观的 demo 感来源。
- **范式缺失**：加载/空态/错误/操作确认没有统一组件，每页各自发明；实时数据靠
  2 秒轮询；`api/client.ts` 泛型默认 `any`，后端改字段前端不报错。
- **样式单体**：index.css 514 行承载全部页面样式，无归属边界。

## 2. 总体路线（四步）

```
第一步:后端收口          第二步:契约打通            第三步:前端设计系统        第四步:运行时升级
(纯重构,行为不变)        (后端→前端类型流)          (视觉+组件范式)           (企业级能力)
─────────────────      ─────────────────────      ─────────────────────     ─────────────────────
T1.1 估值/查询服务收拢   T2.1 API 响应全部 schema 化  T3.1 token 治理+antd 对接   T4.1 SSE 替代轮询
T1.2 数据访问层统一      T2.2 OpenAPI 导出+前端       T3.2 图标体系替换 emoji     T4.2 任务执行器
     (repo+连接池)            类型生成,消灭 any        T3.3 页面范式组件           T4.3 Alembic+列型整治
T1.3 ADR 机制            T2.3 client.ts 类型化重构   T3.4 目录归位+CSS 拆分      T4.4 结构化日志+trace
─────────────────      ─────────────────────      ─────────────────────     ─────────────────────
收益:估值只改一处        收益:后端改字段前端编译报错   收益:视觉上摆脱 demo        收益:多人/生产可用
风险:零(54 条测试护栏)   风险:低                     风险:中(视觉决策主观)       风险:中
```

**排序逻辑**：第一步是地基——服务层不收口，第二步给 API 加 schema、第三步前端接类型
都踩在松动的层上；且第一步零行为变化，现有 pytest 就是护栏。第二步做完前后端才
"长在一起"。第三步解决最直观的 demo 感，放在契约之后做返工最少。第四步是深水区，
按需裁剪。

## 3. 第一步：后端收口（纯重构）

> 目标：每一层只做自己层的事。行为完全不变，54 条 pytest 全绿即验收。

### 任务清单

- [x] **T1.1 抽领域服务层：估值与查询收拢**
  - 新建 `core/valuation.py`：组合净值曲线、日频估值、封场 metrics 的唯一实现。
    `api/resources.py::portfolio_curve/_daily_equity` 与 `engine.py::compute_metrics`
    全部改为调用它；API 层和 engine 里的 `_connect()` 直查 SQL 清零。
  - 新建 `core/queries.py`（或并入 services）：run_rounds/run_round_detail 里
    "从文档反推轮次"的查询逻辑从 API 层收回 core。
  - 环境耦合 hack（日 K 滞后探测）保留逻辑但集中、注释说明前提，不藏在路由里。
- [x] **T1.2 统一数据访问层**
  - `core/db.py` 引入连接池（psycopg_pool），`_connect()` 改为从池取连接。
  - 各 store 的 SQL 留在 store 内（不强制 ORM），但**禁止** store 之外的模块
    调用 `_connect`；加一条 lint/测试护栏守住这条线。
  - `_init_db()` 的 DDL 暂时保留（原地不动），但集中到每个 store 的一个方法里，
    为第四步 Alembic 接管做准备。
- [x] **T1.3 建立 ADR 机制**
  - 新建 `docs/adr/` 目录，把代码注释里的决策（run 336 metrics 归因口径、
    8/24 派生变量事故、附录 14 变量提供器等）逐一抽成短 ADR（背景/决定/后果），
    代码注释改为引用 ADR 编号。
- [x] **T1.4 结构化日志**
  - 引入 `logging` 统一配置，替换 engine/runner/API 里的 `print`；
    日志带 run_id/round/traceId 字段，与前端信封的 traceId 打通。

### 验收

- `uv run pytest -q` 全绿；`web` 构建不受影响。
- `grep -r "_connect" trader/api trader/core/engine.py` 无结果。
- 净值曲线页面数据与重构前一致（人工比对一次）。

### 明确不做

不改 Stage Contract 语义、不改引擎循环机制、不改表结构、不动前端。

## 4. 第二步：契约打通（后端 → 前端类型流）

> 目标：后端字段变更，前端编译期报错。

### 任务清单

- [x] **T2.1 API 响应全部 Pydantic schema 化**
  - 为 runs/portfolios/docs/watchlists/trading 各端点定义 `response_model`
    （当前全部返回裸 dict）。信封结构保持 `{data,status,traceId}` 不变。
- [x] **T2.2 前端类型自动生成**
  - 从 FastAPI OpenAPI 导出（`/api-openapi.json`），用 `openapi-typescript`
    生成 `web/src/api/schema.d.ts`，纳入构建或 pretest 钩子。
- [x] **T2.3 client.ts 类型化重构**
  - `get/post<T>` 的 `T` 接入生成类型，消灭组件里的 `(s: any)`；
    重点页面（Runs/RunDetail/SystemAsset）先行。

### 验收

- 改一个 API 字段名（如 `metrics.return_pct`），`tsc -b` 报出所有受影响组件。
- `oxlint` 无新增 `no-explicit-any` 告警。

## 6. 第四步：运行时升级（企业级能力）

> 目标：多人可用、生产可扛。按实际使用节奏裁剪，不必一次做完。

### 任务清单

- [ ] **T4.1 SSE 替代轮询**：run 实时思考流由 2 秒轮询改为 SSE 推送
  （`run_events` 写入即广播）；保留轮询作为降级。
- [ ] **T4.2 任务执行器**：回放/live 进程从 `subprocess.Popen` 裸拉起，
  改为登记制任务表（状态/日志位置/PID/退出码可查可杀），API 层统一管理。
- [ ] **T4.3 Alembic + 列型整治**：DDL 从 `_init_db()` 迁入 Alembic 版本；
  `prompt_versions` TEXT→JSONB、时间列 TEXT→timestamptz（含存量数据迁移）。
- [ ] **T4.4 观测**：结构化日志落文件 + traceId 全链路（API→core→engine），
  run 详情页可按 traceId 查日志。

### 验收

- 回放可从 UI 发起、查看进度、停止、强杀，全程不碰服务器终端。
- 迁移命令 `alembic upgrade head` 可从空库建出完整结构。

## 7. 执行机制

1. **一个任务 = 一个 PR 级改动**，顺序执行，不并行开工（第一步除外，T1.3/T1.4 可与 T1.1 并行）。
2. 每完成一个任务：跑 `uv run pytest -q` +（涉前端时）`npm run lint && npm run build`，
   然后在本文清单打勾并注明日期。
3. 每步完成后做一次人工走查（对照该步验收标准），再进下一步。
4. 执行中发现新问题时：属于当前步范围的直接做；属于后续步的记入对应任务清单；
   全新事项追加到第 8 节"待裁决"。

## 8. 待裁决

- 是否引入暗色主题（机构终端常见，但 token 已按亮色设计，属于新增需求而非治理）。
- 是否需要消息队列（Redis/ARQ）承载任务执行器，还是 PG 任务表够用（取决于并发场次规模）。

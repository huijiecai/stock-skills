## 2. 系统是什么

Trader 是一个“用 Prompt 描述交易方法、由平台负责运行和留痕”的交易实验与执行平台。

用户主要维护三类内容：

1. 系统的交易方法：系统级 Prompt 和各 Stage Prompt。
2. Stage 的运行协议：单次或循环、运行窗口、上游阶段产物输入、阶段产物输出。
3. 系统级风险策略：联网、自选组写入、模拟交易、实盘交易。

发起一次运行时，用户还可以填写本次任务或分析对象。它是 Run Input，不属于系统的长期配置：
同一个 Stage 和 Prompt 可以先分析一只股票，下一次再分析一个板块，无需修改系统定义。

平台负责以下机制：

- 选择 Prompt 版本并冻结到 Run；
- 绑定用户、系统、组合和运行时钟；
- 每轮组装运行上下文；
- 注册领域工具并记录工具事件；
- 读取上游 Artifact，发布本阶段 Artifact；
- 执行交易账户的现金、持仓、T+1、整手和单票仓位校验；
- 保存 Run、事件、文档血缘、成交和版本历史。

用户不需要在 Stage 中配置行情输入，也不需要在 Prompt 中调用 `save_doc`、`list_docs` 来完成平台存储。
行情、指数、账户、持仓、自选组和研究信息由 Prompt 按需调用领域工具获得。

### 3.1 Web 前端

入口是 `web/src/App.tsx`，主要页面按职责分为：

| 页面 | 作用 |
|---|---|
| `SystemAsset` | 查看某个系统的资产概览 |
| `PromptWorkbench` | 编辑 Prompt、查看版本、预览、查看执行史、试运行领域工具 |
| `SystemSettings` | 编辑 Stage Contract 和系统级风险策略 |
| `DataWorkbench` | 查看自选组和成员 |
| `DocsBrowser` | 查看平台发布的文档产物 |
| `Runs` / `RunDetail` | 查看场次、轮次、工具事件、输入输出血缘，并基于冻结上下文继续讨论 |
| `Coach` | 从系统视角引用多个 Run / Prompt，复盘执行并优化 Prompt |
| `Compare` | 对比不同场次和 Prompt 版本 |

前端通过 `web/src/api/client.ts` 调用 API。所有 API 响应由后端包装为：

```json
{
  "data": {},
  "status": "SUCCESS",
  "traceId": "..."
}
```

前端客户端自动解包 `data`，错误统一转换为异常；`traceId` 同时写入响应头，便于排查问题。

### 3.2 API 层

`trader/api/app.py` 创建 FastAPI 应用，注册路由并在生产模式托管 `web/dist`。

| 路由模块 | 主要职责 |
|---|---|
| `auth.py` | 注册、登录、会话、API Key |
| `systems.py` | 系统和 Manifest、Prompt 版本、Stage Context API |
| `tools.py` | 工具目录和隔离测试调用 |
| `resources.py` | 组合、场次、文档、自选组、交易查询 |
| `chat.py` | 严格分离 Run 结论澄清和 System 教练复盘 |
| `envelope.py` | 统一响应包和 trace id |

API 层负责认证、参数校验、租户入口和 HTTP 状态码；业务状态和执行规则放在 Core 层，避免 CLI、API、测试各自实现一套规则。

### 3.3 Core 平台层

| 模块 | 责任 | 不负责什么 |
|---|---|---|
| `contracts.py` | 解析、规范化、校验 Manifest 和 Stage Contract | 不执行工具、不访问数据库 |
| `context.py` | 保存当前 user/portfolio/run，组装 Runtime Envelope 和 Artifact 输入 | 不主动查询行情、持仓或自选组 |
| `engine.py` | 装配 Agent，驱动 single/loop/replay，管理轮次和重试 | 不定义具体交易方法 |
| `stageio.py` | 解析上游 Artifact，发布阶段 Artifact，记录文档血缘 | 不决定 Prompt 如何交易 |
| `registry.py` | 工具实现注册、用户可见工具组、系统策略过滤 | 不实现工具逻辑 |
| `systems.py` | 系统 Manifest 注册表和内置系统 | 不运行 Stage |
| `runs.py` | Run 的创建、心跳、状态、封场、查询 | 不保存文档正文 |
| `documents.py` | 文档、Artifact、版本、Run 文档关系 | 不决定何时调用模型 |
| `portfolios.py` | 主组合、纸面组合、实验组合和回放开局 | 不实现交易校验细节 |
| `ledger.py` | 钱包、持仓、成交和 T+1 | 不选择标的或生成交易理由 |
| `market.py` | 行情工具和 live/replay 数据边界 | 不保存账户状态 |
| `watchlist.py` | 自选组和成员版本历史 | 不替代 Prompt 的研究逻辑 |
| `events.py` | Run 事件和工具调用留痕 | 观测失败不应杀死主流程 |

## 4. 一次 Stage 运行如何发生

### 4.1 创建或更新系统

```text
用户在 SystemSettings 修改
        │
        ▼
前端 PUT /systems/{slug}/manifest
        │
        ├─ validate_stage_contracts：校验阶段、Artifact 输入输出
        ├─ normalize_manifest：补齐 contract_version、execution、policy
        ├─ 自动创建缺失的 Prompt 初始版本
        └─ Systems.upsert：写入 systems.manifest(JSONB)
```

Manifest 当前仍然是一个 JSONB 文档，而不是 `stages` 独立表。这样适合当前早期阶段：系统定义整体版本化、读写简单、迁移成本低。

示意 Manifest：

```json
{
  "system_prompt": "my-system",
  "policy": {
    "web_search": false,
    "resource_write": false,
    "simulation_trading": true,
    "live_trading": false
  },
  "stages": {
    "observe": {
      "prompt": "observe",
      "kind": "loop",
      "interval": 5,
      "window": "09:35-15:05",
      "inputs": {
        "opening_plan": {
          "kind": "artifact",
          "from": "premarket.plan",
          "selector": "latest",
          "required": false
        }
      },
      "outputs": {
        "decision": {
          "kind": "artifact",
          "label": "本轮判断"
        }
      }
    }
  }
}
```

### 4.2 Stage Contract 的边界

当前 Stage Contract 只保留用户真正需要决定的字段：

| 字段 | 含义 | 用户是否配置 |
|---|---|---|
| `prompt` | 绑定哪条 Prompt | 是 |
| `kind` / `execution.mode` | `single` 或 `loop` | 是 |
| `interval` / `window` / `skip_lunch` | 循环节奏和时间窗 | 是，可使用默认值 |
| `request_limit` | 单轮模型请求预算 | 是，可使用默认值 |
| `inputs` | 上游阶段 Artifact | 是 |
| `outputs` | 本阶段 Artifact | 是，可只填显示名 |
| `policy` | 联网、写入、模拟/实盘交易 | 是，但属于 System 级 |
| `doc_type`、轮次名称、保存动作 | 平台内部存储细节 | 否 |
| 行情、持仓、指数、账户 | Prompt 按需调用的领域数据 | 不在 Stage 中配置 |
| 本次任务、股票或板块 | 启动 Run 时填写的临时目标 | 不在 Stage 中配置 |

输入只能是 `artifact`，并通过 `stage.output` 建立血缘。例如 `live.opening_plan` 引用 `premarket.plan`。
输出通常是 `artifact`，平台内部默认生成 `artifact.{stage}.{output}` 作为存储类型；内置系统仍保留显式旧 `doc_type`，用于已有产物和历史场次继续工作。

### 4.3 Engine 装配 Agent

`engine.build_agent()` 完成以下工作：

1. 按 `system_name + user_id` 读取系统 Manifest。
2. 读取系统级 `policy`。
3. 根据运行模式过滤工具：行情、账户、自选组读取默认提供；写自选组和交易按策略提供。
4. 根据 `web_search` 策略挂载 Web Search。
5. 加载系统级 Prompt。
6. 将工具函数注册到 PydanticAI Agent。

文档工具仍存在于后端代码和高级测试台，用于平台内部和历史流程；它们不属于 Prompt 作者的业务工具目录，也不参与新的 Stage 授权。

### 4.4 Engine 组装上下文

每次模型调用前，Engine 创建 `RuntimeEnvelope`：

```json
{
  "mode": "replay",
  "date": "20260821",
  "clock": "10:35",
  "round": 12
}
```

模型可见的是模式、日期、时钟、轮次、本次 Run Input 和上游 Artifact 内容。例如：

```text
## 本次运行请求

分析沪电股份（002463）今天走势的原因
```

`system`、`stage`、`run_id`、`user_id`、`portfolio_id` 等内部身份只进入运行证据，不直接注入 Prompt。

回放模式另外绑定 `date/clock` 到 ContextVar。交易工具不能通过 Prompt 改写回放日期或时刻，从而避免读取未来数据。

### 4.5 工具调用和交易

```text
Prompt
  │
  ├─ get_quotes / get_indices / get_kline ...
  ├─ get_positions / get_account / get_trades
  ├─ get_watchlist / get_watchlist_quotes
  └─ execute
          │
          ├─ instrument 包装：写入 run_events(tool)
          ├─ 当前 user/portfolio/run ContextVar 隔离数据
          ├─ live/replay/paper 模式边界校验
          └─ ledger 写入 positions / fills / wallets
```

`execute` 的硬校验包括：动作类型、原因必填、整手、主板范围、现金、T+1、单票仓位上限和行情模式。交易理由写入 `fills.reason`，交易行为同时可通过 `run_id` 归因到某次 Run。

### 4.6 Stage 输出和封场

```text
模型最终回答
    │
    ▼
publish_stage_outputs()
    │
    ├─ 计算内部 Artifact 类型、名称和交易日
    ├─ documents.save / resolve
    ├─ run_documents(relation=output)
    └─ RunDetail 可按 Stage、轮次和输出查看
```

循环每轮还会保存 transcript 和轮次 Artifact；Engine 在停止、达到上限或收盘时封存 Run，写入 metrics。

### 4.7 继续讨论和教练复盘

Run 详情提供两个不同入口：

```text
继续讨论
  → 读取该 Run 冻结的 system Prompt 版本
  → 恢复最后一份原始 model transcript
  → 继续以原 Stage Agent 身份回答
  → 不注册交易或写入工具，不写回原 Run 证据

教练复盘
  → 使用独立 _coach Prompt
  → 可显式引用多个 @#Run 和 @prompt
  → 产出系统和 Prompt 改进建议
```

继续讨论默认采用冻结上下文。用户需要运行后的最新数据时，应发起新的 Stage Run，而不是让
讨论线程悄悄改变数据时钟。讨论历史当前保存为 `documents.doc_type=chat`，其中同时保留用于界面
展示的消息和 PydanticAI model message history；教练对话使用 `documents.doc_type=coach`，两者按
Run 与 System 分别归属。

## 5. 数据库设计

### 5.1 数据库与隔离方式

- 数据库：PostgreSQL，连接串由 `DATABASE_URL` 指定。
- 默认 schema：`public`。
- 测试和部分实验可以使用独立 schema；`core.db._connect(schema)` 会设置 `search_path`。
- 业务行同时携带 `user_id` 或 `owner_user`、`portfolio_id`，作为应用层租户隔离轴。
- 当前 DDL 由各 Core store 的 `_init_db()` 幂等执行，并由 `ensure_once()` 保证每个进程/schema 只初始化一次。
- JSONB 主要用于 Manifest、metrics、fields、meta、payload；高频查询字段单独建列和索引。

### 5.2 核心关系图

下图的箭头表示业务上的逻辑关联；当前 DDL 只在身份表和 Prompt 版本表等局部位置使用了外键，
`systems`、`runs`、`portfolios`、`documents` 等核心表之间的完整性主要由 Core 服务和删除流程维护。

```text
users
  │ 1:N
  ├────────────── systems ────────┐
  │                │              │
  │                │ 1:N          │ 1:N
  │                ▼              ▼
  │            prompts        runs ◄─────────────┐
  │                │              │              │
  │                ▼              │              │
  │         prompt_versions      │              │
  │                               │              │
  └────────────── portfolios ◄───┘              │
                    │                            │
          ┌─────────┼──────────┬───────────┐     │
          ▼         ▼          ▼           ▼     │
       wallets   positions    fills     documents │
                                             │    │
                                             ▼    │
                                      run_documents
                                             │
                                             ▼
                                          versions

portfolios ── watchlists ── watchlist_members
runs ── run_events
```

### 5.3 身份和认证表

| 表 | 关键字段 | 作用 |
|---|---|---|
| `users` | `id`, `email`, `display_name`, `is_admin` | 平台用户和租户根 |
| `identities` | `user_id`, `provider`, `identifier`, `credential_hash` | 外部身份或登录凭证映射 |
| `sessions` | `token_hash`, `user_id`, `expires_at`, `revoked_at` | 浏览器登录会话，只存 token hash |
| `api_keys` | `key_hash`, `user_id`, `scope`, `expires_at`, `revoked_at` | CLI/程序调用凭证，只返回一次明文 |

身份模块实现位于 `trader/core/identity.py`。API 通过 `require_user` 把认证结果传递给业务路由。

### 5.4 系统定义和 Prompt 表

#### `systems`

| 字段 | 含义 |
|---|---|
| `id` | 系统内部主键 |
| `user_id` | 系统所属用户 |
| `slug` | 路由和程序使用的稳定标识 |
| `display_name` | 前端展示名 |
| `manifest` | JSONB，包含 system Prompt、stages、policy、doc_classes |
| `status` | `active` 或 `archived` |
| `created_at` / `updated_at` | 生命周期时间 |

唯一性是 `(user_id, slug)`。Stage 不单独建表，当前作为 `manifest.stages` JSONB 的一部分保存。

#### `prompts`

Prompt 的主体索引。`system_id` 非空表示系统命名空间 Prompt，`system_id` 为空表示用户级 Prompt。

#### `prompt_versions`

| 字段 | 含义 |
|---|---|
| `prompt_id` | 所属 Prompt |
| `version` | 递增版本号 |
| `content` | Prompt 正文 |
| `sha256` | 内容哈希，用于判断内容是否变化 |
| `created_at` | 版本创建时间 |

唯一键是 `(prompt_id, version)`。Run 创建时会把实际使用的 Prompt 版本快照写入 `runs.prompt_versions`。

### 5.5 场次、事件和上下文证据

#### `runs`

Run 是定义世界和核算世界的桥。一次 Stage 执行对应一条 Run。

| 字段 | 含义 |
|---|---|
| `id` / `slug` | 场次标识 |
| `kind` | `single`、`live`、`paper`、`replay` 等运行类型 |
| `trade_date` | 业务交易日 |
| `status` | `running`、`stopping`、`sealed` 等状态 |
| `prompt_versions` | 本场使用的 Prompt 版本映射 |
| `system_id` / `stage` | 所属系统和阶段 |
| `portfolio_id` | 本场绑定的组合 |
| `user_id` | 执行用户 |
| `clock` / `clock_date` | real 或 simulated 运行时钟信息 |
| `heartbeat_at` | 长循环心跳 |
| `stage_contract` | 创建 Run 时冻结的 Stage Contract JSONB |
| `run_inputs` | 发起时冻结的本次任务 JSONB，当前使用 `instruction` 字段 |
| `fingerprint` | 回放开局状态指纹 |
| `metrics` | 封场统计 JSONB |

Run 的用户内唯一标识是 `(user_id, slug)`。

#### `run_events`

记录一场 Run 的过程事件：`round_start`、`context`、工具调用、`round_end` 等。

关键字段是 `run_id`、`round`、`kind`、`tool`、`body`。查询索引是 `(run_id, round)`。

#### `run_documents`

记录 Run 与文档的关系：

- `relation=input`：本阶段读取了哪个上游 Artifact；
- `relation=output`：本阶段发布了哪个 Artifact。

此外还保存 `stage`、`slot`、`source_stage`、`source_output`、`content_snapshot`、`meta_snapshot`，用于解释“当时实际看到的内容”，而不是只指向后来可能变化的文档。

### 5.6 组合和账户表

#### `portfolios`

组合是现金、持仓、文档和自选组的隔离边界。

| 字段 | 含义 |
|---|---|
| `owner_user` | 组合主人 |
| `system_id` | 组合所属交易系统 |
| `type` | `main`、`paper`、`experiment` |
| `name` | 展示名 |
| `broker_account_id` | 预留的券商账户映射 |

数据库保证每个 `(owner_user, system_id)` 最多一个 `main` 组合。

#### `wallets`

每个组合一条钱包记录：`cash_cents`、`initial_cents`。金额使用整数分，避免浮点误差。

#### `positions`

每个 `(portfolio_id, code)` 一条当前持仓：数量、可卖数量、成本价分、买入日。主键是 `(portfolio_id, code)`。

#### `fills`

成交流水同时记录资金和行为归因：

- `portfolio_id`：钱记在哪个组合；
- `run_id`：是哪场 Run 的行为；
- `user_id`：哪个用户执行；
- `side`、`quantity`、`price_cents`：成交事实；
- `cash_before/after`、`position_before/after`：核算前后快照；
- `reason`：交易理由；
- `trade_time`：回放时刻或实际成交时刻。

因此，一笔成交可以没有 `run_id`（例如期初或迁移流水），但必须有组合归属。

### 5.7 文档、版本和自选组

#### `documents`

统一保存知识、阶段 Artifact、轮次日志、transcript、Run 讨论和教练记录。主要字段：
`doc_type`、`name`、`trade_date`、`ref_id`、`content`、`meta`、`portfolio_id`、`user_id`。

`doc_type` 是平台内部分类，不是 Prompt 作者需要配置的业务协议。新 Stage 输出没有显式类型时，平台生成 `artifact.{stage}.{output}`。

#### `versions`

统一版本事件表，当前记录 `document` 和 `watchlist` 的全量 payload。关键字段是：
`subject_type`、`subject_id`、`action`、`payload`、`ts`、`portfolio_id`、`user_id`。

#### `watchlists`

组合下的自选组目录，唯一键是 `(portfolio_id, name)`。

#### `watchlist_members`

自选组成员，唯一键是 `(portfolio_id, list_name, code)`。`fields` JSONB 存角色、备注等业务字段；修改会追加到 `versions`。

### 5.8 表之间的关键约束

```text
用户隔离：systems.user_id / runs.user_id / documents.user_id / fills.user_id
组合隔离：wallets / positions / fills / documents / watchlists 都带 portfolio_id
系统归属：portfolios.system_id → systems.id，runs.system_id → systems.id
运行归因：runs.id → run_events.run_id / run_documents.run_id / fills.run_id
产物血缘：run_documents.document_id → documents.id
Prompt 冻结：runs.prompt_versions → prompt_versions 的版本快照语义
```

当前代码以应用层查询条件和 ContextVar 做主要隔离；部分测试还会启用 PostgreSQL RLS 验证数据库层隔离。新增数据访问必须同时考虑 `user_id` 和 `portfolio_id`，不能只依赖默认上下文。

## 6. 三种运行模式

| 模式 | 组合 | 行情 | 交易 | 典型入口 |
|---|---|---|---|---|
| `real` | `main` | live | 只有 `live_trading=true` 才注册 `execute` | `runner live` |
| `paper` | `paper` | live | 只有 `simulation_trading=true`，成交写纸面组合 | Web/CLI 单次或纸面循环 |
| `replay` | `experiment` | replay，日期和时钟由平台绑定 | 只有 `simulation_trading=true`，成交写实验组合 | `runner replay` |

这三种模式不仅是 UI 标签，而是会影响：

- Agent 是否注册交易工具；
- 工具可以请求哪一种行情源；
- 交易写入哪个组合；
- Run 的 `clock`、`clock_date`、`fingerprint` 如何记录。

### 想修改 Stage Contract

### 想修改工具权限

不要在 Stage 添加工具白名单。应修改：

### 想新增一个领域工具

1. 在 `core/market.py`、`core/watchlist.py`、`tools/account.py` 或 `tools/trading.py` 实现；
2. 在 `core/registry.py` 注册到 `TOOLS` 和合适的 `TOOL_GROUPS`；
3. 确认是否是写操作，必要时加入 `WRITE_TOOLS`；
4. 让 API `/tools` 能自省签名和 docstring；
5. 增加工具单测和 ToolPanel 试运行测试；
6. 明确 live/paper/replay 是否允许调用，避免工具自行猜测运行模式。

### 想修改账户核算

优先修改 `core/ledger.py`，不要直接在 API 或 Prompt 工具里改余额。所有成交必须通过 Wallet 统一校验并记录 `fills`。

## 9. 当前实现的有意取舍和后续风险

### 已明确的取舍

- Stage 不保存独立数据库表，先以 Manifest JSONB 管理；
- 用户不配置平台文档存储细节；
- 领域工具默认提供读取能力，副作用通过 System policy 控制；
- 回放上下文由平台绑定，Prompt 不能改变回放时钟；
- 组合是账户、文档、自选组和回放状态的隔离边界。

### 需要持续关注的风险

- 部分历史内置 Manifest 仍保留显式 `doc_type` 和旧 `tools` 字段，属于存量数据兼容，不应重新暴露到新 UI；
- 数据库 DDL 当前由代码启动时执行，未来需要独立 migration 版本管理；
- `user_id`、`portfolio_id` 的隔离同时依赖 API 查询条件、ContextVar 和数据库策略，新增表必须补齐三层检查；
- 工具错误会返回给模型作为文本，新增写工具必须明确失败语义，不能把异常吞成成功；
- 当前前端构建依赖 Node/Vite 版本，CI 应固定 Node 版本并独立执行 Vitest。

## 10. 最短理解路径

如果只想真正理解一次交易系统如何跑起来，建议按这个顺序读代码：

```text
trader/runner.py
  → trader/core/engine.py
  → trader/core/contracts.py
  → trader/core/context.py
  → trader/core/registry.py
  → trader/core/stageio.py
  → trader/core/runs.py / events.py
  → trader/core/portfolios.py / ledger.py
  → trader/core/documents.py
```

读完这条链路，再看：

```text
trader/api/systems.py
trader/api/resources.py
trader/web/src/components/PromptWorkbench.tsx
trader/web/src/components/SystemSettings.tsx
```

这就是平台的主干：

```text
Manifest + Prompt 版本
        ↓
启动时接收 Run Input，Engine 绑定用户/组合/时钟
        ↓
Agent 按系统策略获得工具
        ↓
每轮组装 Context、调用工具、记录事件
        ↓
Ledger 记录交易，Documents 记录 Artifact
        ↓
Run 通过 events/documents/fills 形成完整证据链
```

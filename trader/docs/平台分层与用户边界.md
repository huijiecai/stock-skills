# 平台分层与用户边界 · 设计讨论稿

> 状态:**实现中**。本文是平台边界和减法改造的设计基线。
> 一句话:说清楚"用户该管什么、平台该管什么",作为后续减法改造的施工图。

---

## 1. 北极星:用户来平台做什么

一个用户来平台上,本质上只做一件事:**验证和优化自己的交易系统**。它是一个循环:

```
 ① 想清楚       ② 跑起来        ③ 看见          ④ 判对错        ⑤ 改
 表达假设   →   实盘/回放   →   过程全透明   →   归因(是假设    →   改假设
 (方法论)       (验证装置)      (想/做/为什么)    错还是运气?)      (版本化)
      ↑______________________ 回到 ① 再验证 _____________________↓
```

| 环节 | 用户必须有的 | 现状 |
|---|---|---|
| ① 想清楚 | 写方法论的地方(prompt 就是用户的编程语言) | ✅ 指令台(已 IDE 化) |
| ② 跑起来 | 实盘 + 回放(回放是验证核心:同一天、改一版、重演对比) | ✅ |
| ③ 看见 | 每轮思考流、每笔交易的理由 | ✅ 最强项 |
| ④ 判对错 | 按版本分组的战绩、两场对比 | ⚠️ 有雏形,"决策级对比"是短板 |
| ⑤ 改 | 版本化 + 改完能马上回到② | ✅ |

**判断新功能的标准:它在循环的哪个环节?不在循环上的,不该出现在用户面前。**

## 2. 目标态:稳定材料分三层,每次运行另有一个任务

比喻:**前两层是入职培训(公司制度),第三层是岗位职责(你怎么干这行)**。

```
① 平台基底 —— 代码内置,所有系统一样,用户不可见
   "你在轮次循环里干活;回放只能用当时已发生的数据;每轮落轮日志;
    交易必留痕;T+1/整手由下单工具校验…"

② 本系统的知识库说明 —— 从用户填的一张表自动生成
   "预期 = 一份文档,stage 有这六个值,池子怎么挂…"
   (填错当场被拦,平台知道合法值)

③ 用户的系统设定 —— 用户唯一要写的,纯交易思想
   "基于预期管理交易;六类轮转;买入八条;卖出双出口;14:50 后不开仓…"
   一个工具语法都没有

④ 本次任务 —— 用户点击运行时填写,不属于系统长期配置
   "分析沪电股份(002463)今天走势的原因"
   或"分析 PCB 板块未来一周强弱"
```

前三层回答“这个系统长期如何工作”，第四项回答“这一次具体分析谁、解决什么问题”。
本次任务会冻结到 Run 并进入模型上下文，但不会写回 Stage 或 Prompt。

## 3. 边界怎么画:三问定去留

对任何一条信息问三个问题:

1. **换个作者,答案会不一样吗?** 会 → 作者决定;不会 → 平台定死
2. **作者用大白话答得上来吗?** "产物给人看叫什么?"答得上来 → 该问作者;"doc_type 填什么?"作者不该需要知道 → 平台内部
3. **不填会坏吗?** 会 → 必答;不会但有偏好 → 可选项,**永远带默认值**

三层清单:

| 层 | 内容 | 例子 |
|---|---|---|
| 作者必答 | 业务语义 | 有哪些阶段、每个阶段的 prompt、知识类型长什么样、硬纪律 |
| 作者可选(带默认) | 表现与节奏 | 产物显示名、开局带哪些前序产物、轮间隔、请求上限 |
| 平台自动 | 一切机制 | 文档怎么存、r1/r2 命名、思考流落库、断点接续、证据链、指标 |

自检标准:**"30 秒创建"**——新作者建一个能跑的系统,必答只有 3 个:系统叫什么、阶段怎么组(选模板)、prompt 写什么。

## 4. 工具:按角色分,白名单收缩成几乎零配置

| 角色 | 工具 | 结论 |
|---|---|---|
| **眼睛**(行情类 11 个) | 报价/K线/板块/涨停/扫描 | 默认全给。方法论管"看什么、看完怎么想",不靠蒙眼睛立纪律 |
| **记忆**(文档 4 + 自选组 4) | 存取文档、池子 | 平台内置,配合第②层的知识库说明 |
| **手**(下单 1 个) | execute | 由盘别决定:模拟盘里下单自然是纸面单,不需要勾选 |

剩下真正可选的只有:**联网搜索开关**(已有)。

## 5. 知识类型:填表格,不写文章

现在用户在系统设定里**手写一百多字**教 AI"预期怎么存";
改成在设置页**填一张表**(预期有哪些字段、每个字段哪些合法值),平台负责:生成教 AI 的说明 → 填错拦截 → 按类型筛选展示。

配套的过渡规则(①②建成前,系统设定里提到工具时):**写语义和纪律,不写参数拼写**(参数说明 AI 自动可见)。

## 6.1 Stage Runtime Contract v2 当前落地

Stage Contract 已从单纯的文档衔接扩展为运行契约，当前代码边界如下：

| 契约部分 | 平台行为 |
|---|---|
| `inputs` | 只允许 `artifact`，由阶段血缘解析；行情、组合和研究数据由 Prompt 按需调用工具 |
| `policy` | 系统级配置联网、自选组写入、模拟交易和实盘交易；阶段不再配置能力白名单 |
| `outputs` | `artifact` 自动发布，存储分类、名称和归档由平台生成 |
| `execution` | 统一描述 single/loop、窗口、间隔、请求预算和重试策略 |
| `Run Input` | 发起时填写本次任务或分析对象；不属于 Stage 配置，并随 Run 冻结 |
| `Run` | 冻结 Stage Contract 和 Run Input；每轮记录运行信封、输入证据、工具事件和输出血缘 |

因此，用户修改交易系统时主要关注 Stage 的业务输入和 Prompt；运行某个通用分析 Stage 时，
只需临时填写本次分析对象，不用改系统定义。用户也不再需要在 Prompt 中编排
`list_docs`、`save_doc`、`doc_type`、轮次文档命名等平台机制。

Run 结束后的对话也分两种：

| 对话 | 归属 | 目的 | 上下文 |
|---|---|---|---|
| 继续讨论 | Run | 解释、澄清和补充本场结论 | 原 Stage 身份、冻结 Prompt 和原始 transcript |
| 教练复盘 | System | 对比执行、识别方法问题、优化 Prompt | 显式引用的 Run 和 Prompt |

继续讨论不能修改 Prompt 或覆盖原产物；教练也不能冒充原 Stage Agent 改写本场结论。
